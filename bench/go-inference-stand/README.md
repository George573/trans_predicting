# Пульт прогноза: голова CNN в Go, модель на каждый запрос

Go-сервис с интерактивным UI и CNN из `tram_forecast` (boarding-only, горизонт 61 день).
Каждое действие в интерфейсе отправляет настоящий HTTP-запрос: Go разбирает его, сам
считает голову сети на каждую пару маршрут x день, умножает на коэффициенты и сворачивает
до часов или дней. Кэша ответов нет, Python и PyTorch в рантайме нет.

## Запуск

Из корня репозитория. Нужны чекпойнт `outputs/boarding_only_61days_v5_final/final.pt` и
`dataset/labels/labels_day_test.csv`, оба в git не лежат.

```bash
docker compose up -d --build                   # http://127.0.0.1:8090
STAND_AUTH=jury:secret docker compose up -d    # то же под basic auth
```

Другой чекпойнт: `docker compose build --build-arg CHECKPOINT=outputs/.../final.pt`.

Без Docker:

```bash
pip install -e .
python -m tram_forecast export-head --checkpoint outputs/boarding_only_61days_v5_final/final.pt \
    --labels dataset/labels/labels_day_test.csv --output head.json
cd bench/go-inference-stand && go run ./cmd/server -model ../../head.json
```

## Как считается прогноз

Сеть состоит из энкодера истории (504 часа -> вектор 672) и головы:
`Linear(685 -> 250) -> GELU -> Linear(250 -> 24) -> softplus x scale`. Вход головы - вектор
истории, эмбеддинг маршрута (8), sin/cos дня недели и дня месяца (4) и lead (1).

- История 11-31 октября и эмбеддинг у каждого маршрута фиксированы. Поэтому `export-head`
  при сборке образа прогоняет энкодер на torch и сразу умножает историю и эмбеддинг на их
  часть первого слоя: получается 250 чисел на маршрут. Это точная перестановка слагаемых,
  а не аппроксимация.
- На запрос Go считает всё, что зависит от даты: календарь и lead (5 x 250), GELU, второй
  слой 250 x 24 и softplus. Строки идут блоками по 4, чтобы веса второго слоя читались один
  раз на блок. erf в GELU - рациональная аппроксимация float32 (ошибка 3e-7), softplus -
  `max(x, 0) + log1p(e^-|x|)`, где log1p - многочлен Чебышёва 9-й степени (ошибка 3e-9):
  `math.Log1p` в Go медленный и занимал пятую часть времени.
- История строится тем же `schema.label_grid`, что и при подготовке данных для обучения.
  Сверка: `scale` чекпойнта в точности равен среднему по labels январь-октябрь.
- В `head.json` лежат 27 дней, посчитанных torch целиком. Сервер при старте считает весь
  горизонт и сверяет с ними (допуск 1e-4). При расхождении он не запускается.
  `tests/test_head_export.py` проверяет разложение на случайных весах.
- Маршрут 5 пуст в истории, сеть его не видела: сервис отдаёт 0, как `predict.py`.

## Что есть в UI

- **Управление слева**: маршрут (Shift/Cmd-клик - несколько, "Все" - обзор), период
  (день, неделя, месяц, ноябрь-декабрь), по часам или по дням, три корректирующих
  коэффициента. При изменении запрос уходит сразу.
- **Запрос**: URL, статус, сколько строк посчитала модель, время модели, сервера и полного
  пути до браузера. Полоса показывает, куда ушло время: разбор, CNN, свёртка и k, JSON,
  сеть. Цифры берутся из заголовка `Server-Timing`.
- **Прогноз**: один маршрут - столбцы по часам или линия по дням, несколько маршрутов -
  тепловая карта маршрут x время.
- **Как посчитана точка**: клик по столбцу или клетке шлёт `/api/v1/explain` и
  показывает весь путь: окно истории и среднее по этому часу в тот же день недели, вход
  головы сети, выход модели, умножение на k и число в ответе.
- **Сценарии**: типичные запросы диспетчера, тяжёлый запрос на 270 строк и запрос с
  ошибкой, чтобы увидеть ответ 400.
- **Нагрузка из браузера**: 1-12 параллельных потоков на 15 секунд. RPS, CPU и память
  сервис отдаёт сам через `/api/v1/stats`.
- **Ответ сервиса** и **журнал**: JSON ответа и последние 12 запросов; клик по строке
  журнала повторяет запрос.

## API

Всё под basic auth (`-auth user:pass`), кроме `/healthz`.

```
GET /api/v1/forecast?route=7,11&from=2025-11-10&to=2025-11-16&granularity=hour|day
                    &k_weather=0.9&k_event=1.1&k_season=1.0
GET /api/v1/explain?route=7&date=2025-11-10&hour=8&k_weather=0.9
GET /api/v1/forecast/export?...как forecast...   -> CSV (;)
GET /api/v1/model                                 -> модель, окно истории, горизонт
GET /api/v1/stats                                 -> счётчики запросов, строк, CPU, память
GET /healthz
```

- `route` - список через запятую, пусто = все маршруты.
- `granularity=hour` - не больше 31 дня; неделя и месяц по дням (по QA-сессии).
- `k_*` перемножаются и умножают прогноз.
- Ответ forecast: `{"start": "2025-11-10T00:00", "step": "1h", "k", "series": [{"route",
  "total", "peak_index", "values": [...]}], "meta": {"rows", "model", "timings"}}`.
  Время точки i = `start + i * step`.
- Ошибки: `{"error": {"code", "message"}}` с понятным текстом (400/401).

## Производительность

Микс запросов диспетчера из `scripts/gen_urls.py` (в среднем 20 строк на запрос).
Нагрузку даёт `cmd/load` в той же сети compose. Docker Desktop на Apple M-серии, сервису
отданы 2 ядра, как на проде (`cpuset: "0,1"`), генератору нагрузки - остальные.

| Вариант | Макс. RPS | p50 / p95 при 8 потоках | Память |
|---|---:|---:|---:|
| Python-раннер на ONNX Runtime + Go | 3 700 | 1.66 / 5.74 мс | 150 МБ |
| Два процесса раннера | 4 650 | 1.19 / 5.39 мс | 205 МБ |
| Голова в Go | 23 200 | 0.18 / 1.24 мс | 11 МБ |
| + блоки по 4 строки | 27 500 | 0.16 / 1.02 мс | 11 МБ |
| + softplus многочленом | 30 000 | 0.15 / 0.91 мс | 9 МБ |

- С раннером CPU уходил на HTTP-сервер Python и JSON: из ~300 мкс на запрос сама сеть
  занимала 7-35 мкс. Один процесс упирается в GIL, второй добавляет только 25%: на двух
  ядрах им тесно рядом с Go.
- Голова на одном ядре, микросекунды на вызов:

  | Строк | PyTorch | ONNX Runtime | Go |
  |---:|---:|---:|---:|
  | 1 | 30 | 8.5 | 3.1 |
  | 270 | 207 | 206 | 490 |

  На больших пачках ONNX Runtime быстрее за счёт SIMD, но в сумме Go выигрывает: нет
  второго HTTP-прыжка, JSON между процессами и GIL.
- Большую часть CPU запроса по-прежнему занимает голова: Go считает её скалярно, без SIMD.
  Лёгкий запрос сервер обрабатывает за ~0.07 мс, а задержка на 300 RPS (p50 1.2 мс) почти
  целиком состоит из сети Docker Desktop: пустой `/healthz` даёт там 1.0 мс.
- Деление тяжёлого запроса между двумя ядрами не ускорило ни одиночные запросы, ни
  пропускную способность, поэтому его нет.

## Ограничения

- Голова написана в Go вручную. Если в чекпойнте поменяется архитектура головы, нужно
  править `export-head` и `cmd/server/model.go`: сверка при старте такое не пропустит.
- Постобработка сабмита (калибровка route x weekday, `fill_route5`, новогодний блок) в
  сервис не перенесена, сервис отдаёт сырой прогноз CNN.
- Отсечка модели 1 ноября, поэтому горизонт - ноябрь-декабрь 2025.
