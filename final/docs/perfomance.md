# Производительность

## Статус

В ветке `feature/cnn` опубликованы результаты нагрузочного эксперимента и генератор нагрузки,
но сырые логи и отдельные артефакты замера ещё не переданы в итоговый пакет. Более того,
на текущей вершине ветки отсутствует CLI, необходимый Dockerfile для экспорта модели.
Поэтому числа ниже считаются историческими предварительными результатами и должны быть
подтверждены повторным прогоном после восстановления сборки.

Имя файла `perfomance.md` сохранено в соответствии с согласованной структурой, несмотря на
общепринятое английское написание `performance`.

## Стенд

- Docker Desktop на Apple Silicon;
- сервер ограничен двумя CPU (`cpuset: "0,1"`);
- генератор нагрузки работает в той же compose-сети на остальных ядрах;
- микс запросов формируется `service/scripts/gen_urls.py`;
- в среднем запрос возвращает около 20 строк;
- измеряются RPS, p50, p95 и память;
- сравниваются Python/ONNX runtime и перенесённая в Go голова CNN.

## Опубликованные результаты

| Вариант | Максимальный RPS | p50 / p95 при 8 потоках | Память |
|---|---:|---:|---:|
| Python ONNX runner + Go | 3 700 | `1.66 / 5.74 мс` | 150 МБ |
| Два runner-процесса | 4 650 | `1.19 / 5.39 мс` | 205 МБ |
| Голова CNN в Go | 23 200 | `0.18 / 1.24 мс` | 11 МБ |
| Go, обработка блоками по 4 строки | 27 500 | `0.16 / 1.02 мс` | 11 МБ |
| Go + полиномиальный softplus | **30 000** | **`0.15 / 0.91 мс`** | **9 МБ** |

Это существенно лучше ориентира кейса — сотни RPS при p95 меньше 200–300 мс и памяти
2–4 ГБ. Однако сравнение корректно только после повторения на финальной версии модели.

## Микробенчмарк головы

| Число строк | PyTorch | ONNX Runtime | Go |
|---:|---:|---:|---:|
| 1 | 30 мкс | 8.5 мкс | 3.1 мкс |
| 270 | 207 мкс | 206 мкс | 490 мкс |

На коротких запросах Go выигрывает за счёт отсутствия второго HTTP-перехода, JSON между
процессами и GIL. На большой пачке ONNX быстрее благодаря SIMD, но сквозной сервис всё равно
выигрывает от одного процесса.

Пустой `/healthz` в Docker Desktop имеет задержку около `1.0 мс`, поэтому при умеренной
нагрузке значительная часть клиентской задержки относится к виртуальной сети, а не к модели.

## Что нужно получить вместе с артефактами

Для финального отчёта нужны:

1. точная команда запуска `cmd/load`;
2. commit и checksum чекпойнта;
3. версия Docker Desktop, macOS и модель CPU;
4. ограничения CPU/RAM контейнера;
5. длительность прогона и число warm-up запросов;
6. сырые результаты каждого сценария;
7. error rate и число таймаутов;
8. p99, CPU и RSS во времени;
9. результат длительного стабильностного прогона;
10. повторение после обновления Go-головы под последнюю CNN.

## План контрольного теста

Финальная матрица должна включать:

| Сценарий | Параметры |
|---|---|
| лёгкий | один маршрут, один день, по часам |
| типовой | один-два маршрута, неделя |
| месячный | все маршруты, месяц, по дням |
| тяжёлый | все маршруты, 61 день |
| export | CSV для месячного и полного периода |
| explain | случайные точки разных маршрутов |
| mixed | распределение типовых запросов диспетчера |

Для каждого сценария фиксируются RPS, p50/p95/p99, среднее и пиковое CPU, RSS, размер ответа,
ошибки и конфигурация контейнера. Отдельно проверяется 30-минутный steady-state, чтобы
исключить рост памяти.

## Ограничение применимости текущих цифр

Последняя CNN использует более широкую голову (`859→320→320→24`) и дополнительные входы.
Опубликованный Go-сервис описывает предыдущую более компактную голову. После переноса новой
архитектуры производительность может измениться; существующие числа нельзя автоматически
приписывать финальной модели.
