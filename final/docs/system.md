# Системный дизайн

Из чего состоит решение, как компоненты связаны между собой, как проходит запрос, как
собирается и запускается сервис, и что из спроектированного уже реализовано.

Диаграммы ниже отрендерены из исходников Mermaid и PlantUML, которые лежат рядом, в
[diagrams/](diagrams/): их можно править и перерисовывать.

## Общая схема

![Общая схема решения](img/diagram-system-overview.svg)

Решение делится на два контура, связанных только артефактами:

- **обучение, Python** - готовит почасовую сетку, обучает модели, собирает файл прогноза для
  платформы и экспортирует модель для сервиса;
- **сервис, Go** - держит модель в памяти, считает прогноз на каждый запрос и отдаёт его через
  HTTP API и встроенный интерфейс. Python и PyTorch в рантайме сервиса нет.

Разделение соответствует модульной схеме кейса: приём и нормализация данных -> признаки и
геопривязка -> ML-прогноз и агрегация -> API -> интерфейс.

## Компоненты

![Компоненты](img/diagram-components.svg)

| Компонент | Что делает | Технологии |
|---|---|---|
| Подготовка данных | сырые валидации -> плотная сетка `маршрут x дата x час`, успешные валидации по времени валидации, нули в пропущенных часах | Python, pandas |
| Календарь и события | производственный календарь из XML, расписание заранее известных событий, проверка полноты | Python |

| Ансамбль | четыре модели, бэктест, подбор весов, калибровка, постобработка, файл прогноза | CatBoost, scikit-learn, PyTorch |
| Экспорт головы | прогон энкодера по истории маршрутов, сворачивание постоянной части первого слоя, эталонные дни | PyTorch |
| Go-сервис | HTTP API, basic auth, голова CNN на каждый запрос, коэффициенты, свёртка до часов или суток, CSV | Go, стандартная библиотека |
| Встроенный UI | одностраничный интерфейс диспетчера, раздаётся тем же бинарником | HTML, JavaScript |
| Нагрузочный клиент | заданный RPS или максимум, микс запросов диспетчера, p50/p95/p99, CPU и память сервиса | Go |
| Резервный стенд | тот же API и UI поверх CatBoost из ансамбля | Go, C-библиотека CatBoost |

## Как проходит запрос

![Путь запроса](img/diagram-request-sequence.svg)

На запрос сервис для каждой пары «маршрут x день» считает голову сети, умножает результат на
коэффициенты и сворачивает до часов или суток. **Кэша ответов и предрасчёта нет сознательно**:
модель считает быстрее, чем браузер отрисовывает ответ. Каждое действие в интерфейсе отправляет
настоящий запрос, и время запроса показывается прямо в интерфейсе.

Время разбито по стадиям (разбор, модель, свёртка, JSON) и отдаётся в заголовке
`Server-Timing` и в поле `meta.timings`, чтобы было видно, куда уходят миллисекунды.

## Как модель попадает в Go

![Экспорт головы и проверка при старте](img/diagram-startup-check.svg)

История маршрута и его эмбеддинг при фиксированной дате отсечки не меняются между запросами.
Поэтому при сборке образа PyTorch один раз прогоняет энкодер по истории каждого маршрута и
умножает вектор истории и эмбеддинг на их часть весов первого слоя головы: получается
константа на маршрут. На запрос Go досчитывает только зависящее от даты: вклад календаря и
lead, активации, остальные слои и softplus. Это точная перестановка слагаемых, а не
аппроксимация модели.

Оптимизации Go-реализации: строки считаются блоками по 4, чтобы веса второго слоя читались один
раз на блок; `erf` в GELU - рациональная аппроксимация (ошибка 3e-7); `log1p` в softplus -
многочлен Чебышёва 9-й степени (ошибка 3e-9), потому что стандартный `math.Log1p` занимал
пятую часть времени.

**Защита от рассинхронизации.** В экспорт включаются дни, посчитанные PyTorch целиком. При
старте сервер пересчитывает весь горизонт и сверяет с ними; при расхождении больше 1e-4 он не
запускается, а `/healthz` не отвечает. Несовместимая версия модели не может молча попасть в
работу.

Для резервного CatBoost тот же принцип: модель загружается официальной C-библиотекой, категории
хэшируются один раз функцией библиотеки (в 4.4 раза быстрее, чем передача строк), признаки
календаря считаются в Go по тем же формулам. Прогноз Go совпадает с Python бит в бит на всей
сетке ноября-декабря.

## API

Всё под basic auth, кроме `/healthz`. Ответы - JSON в UTF-8.

| Метод | Назначение |
|---|---|
| `GET /api/v1/forecast` | прогноз по маршрутам, периоду и детализации |
| `GET /api/v1/explain` | разбор одной точки: путь от входа модели до числа в ответе |
| `GET /api/v1/forecast/export` | то же, что forecast, в CSV с разделителем `;` |
| `GET /api/v1/model` | модель, окно истории, горизонт |
| `GET /api/v1/stats` | счётчики запросов и строк, CPU, память |
| `GET /healthz` | готовность: модель загружена и прошла сверку |

Пример запроса и ответа:

    GET /api/v1/forecast?route=7,11&from=2025-11-10&to=2025-11-16
        &granularity=hour&k_weather=0.9&k_event=1.1&k_season=1.0

    {"start": "2025-11-10T00:00", "step": "1h", "k": 0.99,
     "series": [{"route": 7, "total": 118903, "peak_index": 8, "values": [...]}, ...],
     "meta": {"rows": 14, "model": "...", "timings": {...}}}

- `route` - список через запятую, пусто - все маршруты;
- `granularity=hour` - не больше 31 дня; неделя и месяц отдаются по суткам, как попросил
  заказчик на QA-сессии;
- `k_*` - корректирующие коэффициенты погоды, события и сезона, перемножаются и умножают
  прогноз;
- время точки `i` равно `start + i * step`;
- ошибки: `{"error": {"code", "message"}}` с понятным русским текстом, коды 400, 401, 500.

## Интерфейс

Одна страница, управление слева, рабочая область справа, тёмная тема диспетчерского экрана.

- **Управление:** маршрут (один, несколько, все), период (день, неделя, месяц, ноябрь-декабрь),
  по часам или по суткам, три коэффициента. Запрос уходит сразу при изменении.
- **Прогноз:** один маршрут - столбцы по часам или линия по суткам; несколько маршрутов -
  тепловая карта «маршрут x время».
- **Как посчитана точка:** клик по столбцу или клетке показывает весь путь - окно истории и
  среднее по тому же часу и дню недели, вход головы сети, выход модели, умножение на
  коэффициенты и итог.
- **Запрос:** адрес, статус, число строк модели, время модели, сервера и полного пути, полоса
  разбивки времени по стадиям.
- **Сценарии:** типичные запросы диспетчера, тяжёлый запрос и запрос с ошибкой, чтобы увидеть
  ответ 400.
- **Нагрузка из браузера:** 1-12 параллельных потоков на 15 секунд, RPS, CPU и память сервиса.
  Браузер держит не больше 6 соединений на сайт, поэтому это оценка снизу; честный замер делает
  нагрузочный клиент.
- **Журнал:** последние 12 запросов, клик повторяет запрос.

## Сборка и запуск

![Сборка и развёртывание](img/diagram-deployment.svg)

Образ собирается в три стадии: Python-стадия экспортирует голову из чекпойнта, Go-стадия
компилирует статический бинарник, итоговый образ `scratch` содержит только бинарник и файл
головы и запускается от непривилегированного пользователя. Запуск - одной командой Docker
Compose, интерфейс на порту 8090, basic auth включается переменной окружения с логином и
паролем. В той же сети compose работает нагрузочный клиент, сервису выделены два ядра.

## Целевая архитектура

![Целевая архитектура сервиса](img/diagram-target-architecture.svg)

Текущий сервис - рабочий прототип. Спроектирована и описана контрактом OpenAPI 3.1 следующая
версия; её ключевые решения:

- **Версионированный бандл.** Сервис при старте загружает папку артефактов целиком: модель,
  калибровку `маршрут x день недели`, эмпирический коридор, постобработку (маршрут 5, новогодний
  блок), каталог условий, перечень признаков и метаданные обучения.
- **Слой условий вместо трёх плоских множителей.** Шесть условий двух классов:
  **оперативные** (дождь, температура, событие, задержка трамвая) - на горизонтах день и неделя;
  **структурные** (отмена, изменение маршрута) - на любом горизонте. У каждого условия паспорт:
  единица, источник со ссылкой, измеренный эффект с 95%-м интервалом, объём выборки,
  допустимые горизонты. Область условия задаётся маршрутами, датами, днями недели и часами.
  Композиция - произведение, выход за разумный коридор - предупреждение, а не тихое усечение.
- **Аудит в каждом ответе:** базовое значение, применённые условия с их вкладом, итог. Условие,
  неприменимое на выбранном горизонте, возвращается с `applied: false` и предупреждением.
- **Коридор** из эмпирических квантилей остатка по маршруту и полосе часов, расширяемый по
  классу горизонта (см. [research-horizon.md](research-horizon.md)).
- **Два режима модели, которые не смешиваются:** метрический (погода - признак модели, так
  собирается файл для платформы) и сервисный (погода - условие, чтобы коэффициент можно было
  показать и изменить). Одна и та же погода не может быть и признаком, и множителем.
- **Горизонты день, неделя, месяц, сезон** - одна модель, разный объём доступной информации.
- **Дашборд на React и TypeScript** с картой Leaflet по статичному GeoJSON всех десяти линий:
  цвет линии - процент от обычного уровня для этого маршрута, дня недели и часа, а не
  «заполнение»; остановки - только геометрия, без чисел.
- **Экспорт CSV и XLSX** того, что на экране.

Решение «все условия сценарные, автоматического применения нет» - измеренное: поправка на
дождь, применённая автоматически, двигает почасовую WAPE на +0.013 пункта с интервалом через
ноль, а фиксированные температурные коэффициенты делают хуже. Эффекты реальны, но дождливых
часов около 10%, а дневная ошибка нормы и без факторов около 10%.

## Масштабирование и надёжность

- Сервис без состояния: модель читается при старте, между запросами ничего не хранится. Это
  позволяет масштабировать его горизонтально за любым балансировщиком.
- Память стабильна: около 10 МБ на экземпляр для головы CNN, около 30 МБ для CatBoost.
- Ошибки параметров возвращаются кодом 400 с текстом, пригодным для показа пользователю;
  неверные учётные данные - 401.
- Несовместимая модель не запускается благодаря сверке при старте.
