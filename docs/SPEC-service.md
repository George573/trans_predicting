# Спека: сервис прогноза (бэкенд, инференс, слой условий)

Термины - по [CONTEXT.md](../CONTEXT.md). Архитектура модели - в [MODEL.md](../MODEL.md).
Исходный стенд - ветка `go-inference-stand`, папка `bench/go-inference-stand`.

## Problem Statement

Диспетчеру нужен прогноз посадок на выбранных маршрутах за выбранный период, и нужна
возможность спросить «а что будет, если пойдёт дождь» или «если перекроют маршрут»,
получив ответ сразу же. Сейчас есть обученная модель, которая живёт в питоновском скрипте
и умеет только собрать CSV на ноябрь-декабрь, и есть стенд на Go, который считает прогноз
по HTTP, но отдаёт сырой выход модели, умеет только три плоских множителя и ограничен
2025 годом.

## Solution

Go-сервис, который держит в памяти версионированный бандл артефактов, на каждый запрос
строит признаки, прогоняет CatBoost, применяет калибровку и постобработку, затем применяет
условия из запроса и возвращает прогноз вместе с аудитом поправок. Кэша и прекомпьюта нет
сознательно: полная сетка ноябрь-декабрь считается за 11 мс, поэтому любой запрос
диспетчера дешевле, чем его отрисовка.

Фронтенд - отдельная спека, [SPEC-frontend.md](./SPEC-frontend.md).

## Бандл

Папка с версией; сервис загружает её при старте целиком и больше к диску не обращается.

| Файл | Содержимое | Откуда |
|---|---|---|
| `model_service.cbm` | CatBoost без погоды: BASE + внутринедельные sin/cos + признаки праздничного блока | обучение тем же кодом, что сабмит |
| `calibration.json` | множители `route x weekday`, усадка 5.0 | `final_ensemble.py` |
| `corridor.json` | квантили остатка по `route x полоса часов` и коэффициент расширения по классу горизонта | новый скрипт по `artifacts/preds/oof_pooled.parquet` |
| `postprocess.json` | доля маршрута 5 (0.0065), новогодние множители по дням и часам | `postprocess.py` |
| `conditions.json` | каталог условий с паспортами | новый файл, значения из `factors/README.md` |
| `features.json` | перечень признаков в порядке подачи в модель, список категориальных | обучение |
| `meta.json` | версия бандла, период обучения, WAPE на фолдах, время обучения | обучение |

Два бандла выходят из одного обучения: **метрический** (погода признаками, им собран
CSV для платформы) и **сервисный** (без погоды, погода приходит условием). Сервис грузит
только сервисный. Причина разделения - в `docs/SPEC-correction-layer.md`: одна и та же
погода не может быть и признаком, и множителем, иначе эффект считается дважды. Следствие,
которое надо произнести в README: дашборд и сданный CSV дают разные числа, разница на
целевой метрике 0.198 пункта в пользу метрического бандла.

`/api/v1/model` отдаёт `meta.json` и состав бандла. `/healthz` отвечает 200 только когда
бандл загружен и прошёл проверки целостности.

## API

**Машиночитаемый контракт - [api/openapi.yaml](../api/openapi.yaml), OpenAPI 3.1.** При расхождении
прав он: этот раздел - пересказ для людей. Примеры ответов, проверенные по схеме, лежат
в `api/examples/`.

Всё под basic auth, кроме `/healthz`. Тело и ответ - JSON, UTF-8.

### `POST /api/v1/forecast`

```json
{
  "routes": [7, 11],
  "from": "2025-11-10",
  "to": "2025-11-16",
  "granularity": "hour",
  "horizon": "week",
  "corridor": true,
  "conditions": [
    {
      "id": "c1",
      "type": "rain",
      "value": 1.2,
      "scope": {
        "routes": [7],
        "dates": ["2025-11-11"],
        "weekdays": null,
        "hours": [16, 22]
      }
    }
  ]
}
```

- `routes` - пусто или отсутствует означает все десять.
- `granularity` - `hour` или `day`. При `hour` период не больше 31 суток.
- `horizon` - `day | week | month | season`. Влияет только на применимость условий и на
  ширину коридора, но не на модель: модель одна.
- `conditions` - не больше 16 записей. `id` задаёт клиент, он же приходит обратно в аудите.
- `scope.dates` - явный список дат. Шаблоны вида «все будни» разворачивает клиент;
  сервер шаблонов не знает.
- `scope.weekdays` - маска 1-7 или `null`. Применяется как дополнительный фильтр к датам.
- `scope.hours` - `[от, до]` включительно, или `null` для всех часов.
- `scope.routes` - `null` означает все запрошенные маршруты.

### Ответ

```json
{
  "start": "2025-11-10T00:00",
  "step": "1h",
  "bundle": "2026-09-27T09:12:00Z/8f3a1c",
  "series": [
    {
      "route": 7,
      "base": [12, 9, 6],
      "value": [12, 9, 6],
      "lo": [10, 7, 4],
      "hi": [15, 11, 8],
      "usual": [13, 10, 7],
      "base_total": 120431,
      "total": 118903,
      "peak_index": 18
    }
  ],
  "conditions": [
    {
      "id": "c1",
      "type": "rain",
      "applied": true,
      "factor": 0.936,
      "contribution_pct": -1.4,
      "points": 7,
      "profile": null,
      "passport": {
        "unit": "мм/ч",
        "source": "Open-Meteo ERA5",
        "source_url": "https://open-meteo.com/",
        "effect_pct": -5.4,
        "ci_pct": [-10.0, 0.0],
        "sample": 1953,
        "horizons": ["day", "week"],
        "class": "operational"
      }
    }
  ],
  "warnings": [
    {
      "code": "condition_not_applicable_on_horizon",
      "condition_id": "c2",
      "message": "Оперативные условия на горизонте месяц не применяются: измеренный эффект меньше ширины коридора"
    }
  ],
  "meta": {
    "rows": 336,
    "model": "catboost_cyclic_service",
    "timings": {"parse": 0.1, "features": 0.6, "model": 1.2, "corrections": 0.2, "json": 0.4}
  }
}
```

- Время точки `i` равно `start + i * step`. Массивы всех серий одной длины.
- `base` - прогноз до условий, `value` - после. При пустом сценарии они совпадают.
- `usual` - обычный уровень для этого маршрута, дня недели и часа. Нужен карте: цвет
  означает процент от обычного, а не заполнение салона.
- `lo`, `hi` - коридор; приходят только при `corridor: true`.
- `conditions[].contribution_pct` - вклад условия в изменение суммы по всему выбору.
- `conditions[].profile` - почасовой профиль эффекта, заполняется только когда запрошен
  один маршрут и одни сутки. В остальных случаях `null`: на месяце по десяти маршрутам это
  в разы больше данных, чем сам прогноз.
- `warnings` - отложенные условия и выход произведения за коридор корректировки. Условие с
  `applied: false` остаётся в ответе: клиент показывает его серым, а не удаляет.

### Остальные точки

```
POST /api/v1/forecast/export?format=csv|xlsx   тело как у forecast, ответ - файл
POST /api/v1/explain                           одна клетка: route, date, hour, conditions
GET  /api/v1/conditions                        каталог с паспортами, без прогноза
GET  /api/v1/routes                            маршруты, названия, есть ли геометрия
GET  /api/v1/model                             бандл и метаданные обучения
GET  /api/v1/stats                             счётчики запросов, строк, CPU, память
GET  /healthz                                  без авторизации
```

- Экспорт отдаёт `Content-Disposition` с осмысленным именем файла; клиент сохраняет blob.
  XLSX собирается `excelize`; зависимость вендорится, потому что `proxy.golang.org` из
  среды сборки может быть недоступен.
- `explain` сохраняет поведение стенда: календарь, все признаки в том виде, в каком они
  ушли в модель, сырой выход, обрезка нуля, калибровка, каждое условие отдельной строкой,
  итог.
- Ошибки: `{"error": {"code", "message"}}`, коды 400, 401, 413, 500. Сообщение - на русском
  и пригодное к показу.

### Пределы

| Что | Предел | Причина |
|---|---|---|
| `granularity=hour` | 31 сутки | объём ответа, не скорость модели |
| строк модели на запрос | 20 000 | всё, что больше, запрашивается по дням |
| условий | 16 | читаемость аудита |
| горизонт дат | 2025-01-01 ... 2026-04-30 | календарь и область определения модели |

## Каталог условий

Шесть условий, два класса. Значения - из `factors/README.md`, эффекты по маршрутам там же.

| Тип | Класс | Единица | Эффект | Горизонты |
|---|---|---|---|---|
| `rain` | оперативное | мм/ч | по маршрутам от -3.1% до -10.0%; общий -6.4% [-10.3; -2.9] | день, неделя |
| `temperature` | оперативное | отклонение от нормы, °C | +3.8% на +10 градусов [+0.6; +7.2]; по маршрутам значим только на 12, 17, 25 | день, неделя |
| `event` | оперативное | процент, задаётся вручную | не измерен, вводится оператором | день, неделя |
| `delay` | оперативное | пост о задержке | -31.7% [-41.2; -23.6] в 0-2 ч; по маршрутам от -8.8% до -39.1% | день |
| `closure` | структурное | маршрут выключен | -97% (отмена), 0 посадок при полном перекрытии | все |
| `route_change` | структурное | изменение на участке | -15% и -17% по наблюдениям Дептранса | все |

Паспорт записи: единица и шаг, источник и ссылка, точечный эффект, границы 95%
интервала, объём выборки, допустимые горизонты, класс, область применения. Эффект
хранится по маршрутам плюс общий как запасной: при выборе одного маршрута показывается
маршрутный, при нескольких - общий.

**Все шесть условий по умолчанию сценарные, автоматического применения нет ни у одного.**
Это измеренное решение, а не осторожность: поправка на дождь, применённая автоматически,
двигает почасовой WAPE на +0.013 пункта [-0.044; +0.065], то есть ни на что, а
фиксированные температурные коэффициенты делают хуже. Эффекты при этом реальные и значимые
на истории - просто дождливых часов около 10%, а норма и без факторов ошибается в дневные
часы в среднем на 10% посадок. В README обе половины этого факта должны стоять рядом.

Композиция - произведение, порядок не важен. Произведение ограничено коридором
корректировки; выход за него - предупреждение в ответе, а не тихое усечение.

## Горизонты

Одна модель на всех горизонтах. Различается объём доступной информации, а не архитектура.

| Горизонт | Квант | Оперативные условия | Структурные | Погода |
|---|---|---|---|---|
| день | час | да | да | условием |
| неделя | сутки, часы вложенно | да | да | условием |
| месяц | сутки | нет, пустое состояние с объяснением | да | климатическая норма, контрол заблокирован |
| сезон, ноя 2025 - апр 2026 | месяц | нет | да | климатическая норма, контрол заблокирован |

Переключение горизонта с заданными условиями: условия **сохраняются, но не применяются**,
в ответе приходит предупреждение, клиент показывает баннер. Ни схлопывания области условия,
ни блокировки переключателя.

Для горизонта дальше 31 декабря 2025 нужен `input/calendar/2026.xml` с того же
xmlcalendar - формат тот же, парсер в `internal/features` менять не нужно.

## Коридор

Считается один раз скриптом по `artifacts/preds/oof_pooled.parquet`: эмпирические квантили
0.1 и 0.9 отношения факта к прогнозу по `route x полоса часов` (ночь, утро, день, вечер).
Коэффициент расширения по классу горизонта берётся из сравнения фолдов, а не назначается.
Результат - таблица в бандле; в рантайме это умножение.

Коридор используется в двух местах: как `lo`/`hi` в ответе и как порог превышения на карте
(превышение - прогноз выше верхней границы для этого часа).

## Testing Decisions

Хороший тест здесь проверяет наблюдаемое поведение на границе модуля, а не внутренности.
Швов два, оба существующие или новые верхнего уровня.

**Шов 1: применение условий.** Функция, принимающая кадр прогноза, контекст и список
условий, возвращающая кадр плюс аудит. Тестируется без модели, на синтетическом прогнозе.
Свойства: пустой сценарий не меняет ни одного числа; условие вне своей области не меняет
ничего; два условия на одни часы дают произведение и не зависят от порядка; условие
неприменимого класса возвращает `applied: false` и предупреждение, а прогноз не меняет;
сумма `contribution_pct` согласована с отношением `total` к `base_total`.

**Шов 2: соответствие Python и Go.** Golden-тест на всей сетке ноябрь-декабрь: сервисный
бандл в Python и сервис на Go дают одинаковые числа. Прототип этого теста уже есть -
`cmd/check` в ветке стенда, он сверяет прогноз с `ref_grid.csv`. Расширяется на калибровку
и постобработку, порог - совпадение до 1e-6 на сыром выходе и до единицы после округления.

Прочее: контрактные тесты на пределы и коды ошибок; нагрузочный `cmd/load` на смеси
запросов диспетчера, числа идут в README.

## Работы и риски

1. `2026.xml`, горизонт до апреля 2026.
2. Экспорт бандла из обучения, два бандла, `features.json`, `meta.json`.
3. Признаки праздничного блока в Go.
4. Калибровка, маршрут 5, новогодний блок в Go; расширение golden-теста.
5. Скрипт коридора, `corridor.json`.
6. `conditions.json` с паспортами и эффектами по маршрутам.
7. Слой условий: классы, области, произведение, аудит, предупреждения.
8. Контракт: POST, новые точки, экспорт CSV и XLSX.
9. Геометрия: статичный GeoJSON по десяти маршрутам, справочник плюс OSM.
10. Docker: debian-slim, glibc, `libcatboostmodel`, статика фронтенда в том же образе.

**Главный риск - пункт 10: образ не собирался ни разу.** Собирать его первым, а не
последним, и проверять на пустом окружении.

Второй риск - геометрия: в справочнике есть маршруты 1, 2, 3, 4, 5, 6, 7, 10, 11, 12, а в
данных 1, 5, 7, 11, 12, 17, 25, 26, 28, 50. Пересечение - пять маршрутов, остальные пять
берём из OSM. Если отношение по номеру окажется битым, этот маршрут остаётся без линии и
живёт в таблицах; остальные не ждут.

## Out of Scope

- Остановочная детализация. Посадок в разрезе остановок в данных нет: `place_id` - это
  депо. Что нужно для настоящей детализации - в плане развития.
- Вместимость, наполнение салона, проценты заполнения. В справочнике `capacity` есть, но
  листы `Расписание` и `Наряд` содержат по 15 строк - это образец формата, а не план
  выпуска.
- Переток спроса при перекрытии маршрута на соседние линии.
- Ноукаст на валидациях последних суток. Обоснование - в `MODEL.md`.
- Приём потоковых данных. Сервис читает бандл, а не поток; поточная часть описана как
  план.
