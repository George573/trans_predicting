# Производительность

Замеры пропускной способности, задержки и памяти сервиса прогноза на развёрнутом стенде
https://mttech.k1rles.ru. Все числа в документе сняты на одном стенде - прод-хосте, в том же
контейнере, который отдаёт дашборд и API. Имя файла сохранено в согласованной структуре
документов.

## Требование кейса

Один контейнер 2-4 vCPU и 2-4 ГБ RAM, держащий сотни RPS при p95 меньше 200-300 мс и
утилизации CPU 60-80% с запасом, память стабильна без swap.

## Стенд

| Параметр | Значение |
|---|---|
| Хост | 2 vCPU Intel Xeon Gold 6240 2.60 ГГц, 3.9 ГБ RAM |
| Сервис | один контейнер Docker: Go-сервер с обеими моделями (CatBoost и CNN) и статикой дашборда, `GOMAXPROCS=2` |
| Нагрузка | `cmd/load` на том же хосте, в `http://localhost:8090` в обход nginx и TLS; генератор делит с сервером те же 2 vCPU |
| Кэш | нет: каждый ответ считается моделью заново |

## Итог

| Показатель | Результат | Требование кейса |
|---|---|---|
| пропускная способность | **100-400 RPS без ошибок** в открытом цикле; **572-582 RPS** в замкнутом цикле вместе с генератором на тех же 2 vCPU | сотни RPS |
| задержка p95 | **15.22 мс** при 200 RPS, 28.76 мс при 300 RPS, 51.46 мс при 400 RPS | меньше 200-300 мс |
| утилизация CPU | 65% ядра при 200 RPS, 121% ядра при 400 RPS - 60% бюджета 2 vCPU | 60-80% с запасом |
| память | **19.65 МиБ** контейнера в простое, 44-47 МБ RSS под нагрузкой, swap нет | стабильна без swap |
| самый тяжёлый запрос смеси | вся сеть на 30 суток по часам: CatBoost **13 мс**, CNN **51 мс** времени модели | - |

При 400 RPS сервис держит p95 в четыре раза ниже порога кейса, используя 60% бюджета
процессора - нижнюю границу зоны 60-80%, которую кейс называет рабочей.

## Методика

- **Нагрузочный клиент** `cmd/load` на Go: замкнутый цикл с заданным числом потоков или
  открытый цикл с заданным RPS (64 соединения); латентности p50/p95/p99/max и число ошибок.
  Задержка - от отправки запроса до конца ответа на стороне клиента.
- **Порядок**: 5 секунд прогрева по 8 потокам, затем замкнутый цикл по 8 и по 2 потока и
  открытый цикл 100, 200, 300, 400 RPS, каждый замер 15 секунд.
- **Смесь запросов** - 4 000 тел запросов `POST /api/v1/forecast` (seed 1), модель CatBoost или
  CNN поровну:

| Доля | Запрос |
|---:|---|
| 60% | один маршрут на сутки по часам, половина с дождём на 16-22 ч |
| 20% | вся сеть на сутки по часам, половина с дождём |
| 15% | один маршрут на 30 суток по дням, горизонт месяц |
| 5% | вся сеть на 30 суток по часам |

  В среднем около 600 строк модели на запрос, средний ответ 8-10 КБ. Каждый ответ несёт
  коридор, обычный уровень и аудит условий.
- **CPU и память** - процесс сервера через `/proc` (`cmd/load -pid`), в процентах одного ядра;
  память контейнера - `docker stats` до и после серии.
- **Время модели на тяжёлый запрос** - часть `model` заголовка `Server-Timing`, медиана 5
  запросов после одного прогревочного: вся сеть одной моделью с коридором и без условий.

Команды, из `service/`: клиент собирается под Linux и копируется на хост вместе с телами
запросов.

    uv run --quiet --python 3.12 python scripts/gen_load.py > bodies.jsonl
    GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o load ./cmd/load
    PID=$(docker inspect -f '{{.State.Pid}}' trans_predicting-server-1)
    ./load -url http://localhost:8090/api/v1/forecast -bodies bodies.jsonl -c 8 -d 5s -label "прогрев"
    ./load -url http://localhost:8090/api/v1/forecast -bodies bodies.jsonl -c 8 -d 15s -pid $PID -label "8 потоков"
    ./load -url http://localhost:8090/api/v1/forecast -bodies bodies.jsonl -rate 200 -c 64 -d 15s -pid $PID -label "200 RPS"

## Нагрузка

| Сценарий | RPS | p50, мс | p95, мс | p99, мс | max, мс | Ошибки | CPU сервера | RSS |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 RPS, открытый цикл | 100 | 1.95 | 15.29 | 55.01 | 98.5 | 0 | 37% | 44 МБ |
| 200 RPS, открытый цикл | 200 | 1.74 | **15.22** | 55.12 | 73.7 | 0 | 65% | 44 МБ |
| 300 RPS, открытый цикл | 300 | 1.96 | 28.76 | 65.32 | 209.9 | 0 | 92% | 44 МБ |
| 400 RPS, открытый цикл | 399 | 2.95 | 51.46 | 114.43 | 319.8 | 0 | 121% | 47 МБ |
| 2 потока, замкнутый цикл | 582 | 0.77 | 12.88 | 53.55 | 112.7 | 0 | 173% | 45 МБ |
| 8 потоков, замкнутый цикл | 572 | 6.38 | 48.07 | 117.43 | 414.5 | 0 | 173% | 46 МБ |

- CPU - процент одного ядра; бюджет контейнера - 200%.
- Медиана задержки при любой нагрузке - 1-3 мс. Хвост p95-p99 дают тяжёлые запросы по всей
  сети на 30 суток по часам: около 6 500 строк модели против 24-720 у остальных.
- В замкнутом цикле сервер получает 173% из 200%, остальное забирает генератор, поэтому
  572-582 RPS - потолок пары «сервер + генератор» на 2 vCPU, а не одного сервиса.
- Память контейнера по `docker stats`: 19.65 МиБ до серии, 29.03 МиБ после.

## Тяжёлые запросы по моделям

![Время модели на тяжёлый запрос](img/perf_heavy.svg)

Вся сеть одной моделью с коридором и без условий, время модели по `Server-Timing`.

| Запрос | CatBoost | CNN |
|---|---:|---:|
| 30 суток по часам, 2025-11-01...2025-11-30 | 13 мс | 51 мс |
| 61 сутки по суткам, 2025-11-01...2025-12-31 | 23 мс | 100 мс |
| 120 суток по суткам, 2026-01-01...2026-04-30 | 47 мс | 197 мс |

Почти всё время запроса - сама модель: разбор, признаки, поправки и JSON вместе занимают
0.4-2.1 мс. CatBoost считает деревья через `libcatboostmodel`, CNN - голову
`859 -> 320 -> 320 -> 24` в Go, по одному проходу на пару маршрут x день. Самый тяжёлый
запрос - CNN по всей сети на 120 суток - укладывается в 197 мс; это одиночный запрос, в смеси
диспетчера таких нет.

## Почему так быстро

- **Модели считаются в Go, без Python в рантайме.** CatBoost - через официальную C-библиотеку с
  категориями, захэшированными один раз при загрузке модели. У CNN при сборке бандла заранее
  посчитаны энкодер истории и постоянная часть первого слоя головы; на запрос остаётся только
  часть, зависящая от даты.
- **Модели и статика в памяти.** Бандлы читаются при старте и сверяются с эталоном, статика
  дашборда отдаётся из памяти с gzip; к диску сервис на запросах не обращается.
- **Нет второго сетевого перехода.** API, модели и интерфейс - один процесс в одном контейнере.

## Что ещё не замерено

- **Сетевой путь снаружи.** Нагрузка подана через `localhost:8090`; путь через nginx и TLS от
  внешнего клиента под нагрузкой не измерялся.
- **Длительный прогон.** Стабильность памяти под нагрузкой за 30 минут не проверялась;
  известна память в простое и в 15-секундных замерах.
- **Сервис отдельно от генератора.** Генератор делит с сервером те же 2 vCPU, поэтому предельный
  RPS одного сервиса выше 570-580 RPS, но насколько - этот замер не показывает.
